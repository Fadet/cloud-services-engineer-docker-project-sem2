# Работа с секретами

## Где что хранится

| Тип | Где хранится | Как попадает по назначению |
|---|---|---|
| Креды реестра для CI | GitHub Secrets (`DOCKER_USER`, `DOCKER_PASSWORD`) | `docker/login-action`, значения маскируются в логах |
| Секреты рантайма | файлы в `secrets/` (гитигнорятся) | Docker secrets → `/run/secrets/<имя>`: `metrics_htpasswd`, `order_id_secret` |
| Несекретная конфигурация | `.env` (гитигнорится), шаблон — `.env.example` | подстановка переменных в compose |

Ничего из перечисленного не попадает в образы: секреты монтируются в контейнер на старте,
а не копируются слоем.

## Правила

1. **Секреты не кладутся в `.env`.** Значения оттуда разворачиваются в переменные окружения
   контейнера и видны в `docker inspect` и в логах. `.env` — только для портов и подобной
   несекретной конфигурации.

2. **Секреты не передаются через `ARG`/`ENV` на сборке.** Значения `ARG` остаются в
   метаданных образа и видны в `docker history`. Если сборке нужен токен (например,
   приватный npm-реестр), используется BuildKit-монтирование, которое не оставляет следа
   в слоях:

   ```dockerfile
   RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
   ```
   ```bash
   docker build --secret id=npmrc,src=$HOME/.npmrc .
   ```

3. **`VUE_APP_*` — публичные значения.** Vue CLI инлайнит их в JS-бандл, который отдаётся
   каждому посетителю. Секрет, переданный так, считается скомпрометированным.

4. **Контекст сборки чистится через `.dockerignore`.** В обоих контекстах исключены
   `.env*`, `.npmrc`, `secrets/`, `*.pem`, `*.key`, `*.crt` — чтобы `COPY . .` не затащил
   локальные креды разработчика в слои builder-стейджа и в кеш сборки.

5. **Рантайм-ограничения снижают ущерб от компрометации**: non-root, `read_only`,
   `cap_drop: [ALL]`, `no-new-privileges`, бэкенд в `internal`-сети без выхода наружу.

## Пример: basic-auth на /metrics

Прометеевские метрики не отдаются наружу без аутентификации. htpasswd приезжает в
балансировщик Docker-секретом и в образе отсутствует.

```bash
docker run --rm httpd:2.4-alpine htpasswd -nbB metrics '<пароль>' > secrets/metrics.htpasswd
chmod 0644 secrets/metrics.htpasswd
METRICS_HTPASSWD_FILE=./secrets/metrics.htpasswd docker compose up -d
```

По умолчанию подставляется коммитящаяся заглушка `secrets/metrics.htpasswd.example` с
заведомо невалидным хешем: поведение fail closed — `/metrics` отдаёт 401 всем, настоящих
кредов в репозитории нет, а CI поднимает стек без предварительной подготовки файла.

Смена значения `METRICS_HTPASSWD_FILE` не пересоздаёт контейнер сама по себе: имя секрета
не меняется, и Compose считает сервис неизменённым. При подмене или ротации секрета нужен
явный `docker compose up -d --force-recreate lb`.

Compose в non-swarm режиме бинд-маунтит файл как есть и игнорирует `uid`/`gid`/`mode`,
поэтому файл должен быть читаем для uid 101 внутри контейнера (`chmod 0644`). Внутри
лежит хеш, а не пароль.

## Пример: подпись идентификаторов заказов

`POST /orders` раньше отдавал инкремент (`1`, `2`, `3`…): id перечислялись, а три реплики,
каждая со своим счётчиком в памяти, гарантированно выдавали одни и те же значения.

Теперь id — это `hex(HMAC-SHA256(secret, instanceNonce || counter))`, обрезанный до 16 байт.
`instanceNonce` — 8 случайных байт из `crypto/rand` при старте процесса, поэтому пара
`(instanceNonce, counter)` глобально уникальна и две реплики физически не могут подать на
вход HMAC одно и то же. Общее хранилище и координация не нужны.

Секрет приезжает Docker-секретом в `/run/secrets/order_id_secret` и в образе отсутствует:

```bash
openssl rand -hex 32 > secrets/order_id.secret
chmod 0644 secrets/order_id.secret
ORDER_ID_SECRET_FILE=./secrets/order_id.secret docker compose up -d --force-recreate backend
```

Если секрет не передан, каждая реплика генерирует временный ключ и пишет WARN в лог. id
остаются непредсказуемыми и уникальными — стойкость обеспечивает случайный `instanceNonce`,
который наружу не выходит, — но перестают быть воспроизводимыми между перезапусками и
одинаковыми у реплик. Общий секрет нужен именно для воспроизводимости и для возможности
позже проверять подлинность id без базы, а не как единственный барьер против перебора.

## Известные замечания по CI (не закрыты намеренно)

Шаги `.github/workflows/deploy.yaml` менять нельзя, поэтому фиксируем как рекомендации:

- нет `permissions:` — `GITHUB_TOKEN` получает права по умолчанию; стоит сузить до
  `contents: read`;
- actions не прибиты к SHA (`@v3`, `@v2`, `@v4`) — риск цепочки поставок при перемещении тега;
- `secrets.DOCKER_USER` используется в теге образа; имя пользователя не секрет, из-за этого
  теги маскируются в логах как `***`. Уместнее GitHub Variables (`vars.DOCKER_USER`);
- `DOCKER_PASSWORD` стоит завести как Docker Hub **access token** с правами только на push,
  а не как пароль аккаунта.
